## 0.3.2 (2026-11-19)

### Added

- `blazon.platform-tokens` writes the width of `border` tokens as a dimension named `<token path>.width` (`border.rule` is `border_rule_width` in `dimens.xml`, `BlazonDimensions.borderRuleWidth`, `BlazonDimens.borderRuleWidth`), so every output and option applies. The colour is not written. A style other than `solid` is named in a new `border-style-dropped` info finding; an unreadable width is a `dimension-unreadable` warning. `include` and `exclude` match the border token's path. `border` leaves the `tokens-skipped` list. A brand with no border token gets the same files.
- `blazon.platform-tokens` takes `include` and `exclude`: lists of token path prefixes in dot form (`["breakpoint", "component.button.website"]`), compared name by name, with no glob or regular expression. `include` keeps only the matching tokens, `exclude` then removes matching ones, in every output and the dark context. A bad list is an `option-invalid` finding; an entry that matches no token is a `filter-unmatched` info finding.
- `blazon.press-kit` takes a `company` option (`description`, `boilerplate` and up to 20 `facts` as `{ label, value }`) for a brand whose own title and description are a book's: the company description replaces the brand's in `about.txt` and the PDF, and the boilerplate and facts follow. It also takes a `note` (one line) printed in `README.txt`, `about.txt`, `colors/colors.txt` and the PDF, for a kit whose colors are not yet approved. A wrong value is an `option-invalid` finding at `options.company...` or `options.note`, with length limits stated in the plugin README. With neither option the files are unchanged except for the fixes below.
- `brand.json` carries the license file that sits beside a font file the config embeds (`OFL.txt`, `LICENSE`, `LICENCE`, `COPYING`, in that file's own folder only) as `theme.fontLicenses`: `{ family, licenseFile, licenseText }`, at most 64 KiB, UTF-8, inside the project. A new optional field, so `version` stays 2. A file that is too large, not UTF-8 or reached through a link out of the project is not read, and `font-license-invalid` (a warning) says why.

### Changed

- The MCP tool `check_brand` says what its counts leave out. A plugin's roles are only in the manifest its program prints, so the server cannot tell a `check` plugin from a build-only one (`blazon.tailwind`, `blazon.shadcn`) without starting it. `pluginsSkipped` still lists every plugin in `blazon.json`; the warning and the tool description now say that only a plugin with a `check` role can add findings, and the warning no longer says the counts "can be higher" without that condition.
- `blazon.press-kit` `fonts.txt` prints the license from that file (`License file:` and its identifying line) for a font whose token states no license, instead of `License: not stated`.
- The `blazon.print-book` docs say its PDF is Chrome's output with lossless images, so it is large, and that a post-processing step such as Ghostscript shrinks it.
- `blazon.platform-tokens`: with a `prefix`, the colorset names in `Colors.xcassets` carry it in lowerCamel (`acmeBlue100`) and the Swift file is `<Prefix>Tokens.swift` (`AcmeTokens.swift`), so generated color symbols do not collide with an app's own assets. With no prefix the output is byte-identical. The Kotlin `package blazon.tokens` stays fixed.
- The `blazon.platform-tokens` README documents `prefix`, what it reaches, the naming rule per output and which token types are not written.
- The release audit allowlist is empty. The picomatch advisory it held (GHSA-fc5q-39xc-vjpf) was withdrawn upstream on 2026-11-18, so `npm audit` is clean again; the gate failed on the stale entry, as designed, and the entry and the SECURITY.md section about it are removed.

### Fixed

- The print book draws a Markdown task item (`- [ ]`, `- [x]`) with no bullet and a visible box: a border in the theme's text color, filled when checked. The browser's own checkbox printed as a nearly invisible pale grey.
- `blazon.press-kit` `fonts.txt` listed system fonts (`SFMono-Regular`, `Arial`) as brand fonts with `License: not stated`. It now lists a family only when it is the front of a stack and not a system font, or a stylesheet or font file loads it, or its token states a source or license; the rest are one last line, `Fallback fonts, not shipped: ...`. With no option the output changes: that line is new, and a system family is gone from the font list and from the `font-license-unstated` finding. A brand whose stacks name only system fonts now gets `font-none` and no `fonts.txt`. The license is still read only from the font token: the plugin gets no project folder, so it cannot read a license file beside the font files.
- `blazon.press-kit` `README.txt` ran the PDF's name into its description (`acme-press-kit.pdfOne page`) when the name was long. The descriptions now start two spaces after the longest name, and at column 16 when the names are shorter, so a kit with short names is unchanged.
- `blazon.press-kit` PDF swatches took the first ten colors in file order, labelled with the last path segment (`500`). They now take whole color groups in the order the brand gives them, labelled with group and step (`blue 500`); a flat color keeps its description. The PDF line of `README.txt` states the rule.
- A quoted family after a comma in a font stack (`'Inter', 'Arial Narrow'`) was read with its quotes by the shipped plugins' stack reader.

## 0.3.0 (2026-11-17)

Tagged and pushed, not released: its release job failed at the dependency audit gate on a high advisory in picomatch (via vite) that has no patched version. Everything in it is part of 0.3.1.

### Added

- The MCP server ships inside `@iksnerd/blazon`. `npm install @iksnerd/blazon` gives you `blazon-mcp` (a second `bin`), and `npx -y -p @iksnerd/blazon blazon-mcp --brand <dir>` starts it with no clone. It is one built file, `mcp/dist/index.js`, with the MCP SDK and zod bundled in at build time, so the package gains no dependency and `npm audit --omit=dev` is unchanged. `blazon-mcp --version` prints the versions it carries.
- `npm run check-pack` requires `mcp/dist/index.js`, fails when a plain path in `package.json` `files` is not in the package, and the tarball smoke test (`scripts/smoke-tarball.mjs`) runs `blazon mcp --check` and a real `check_brand` and `list_tokens` through the installed server.

### Changed

- `blazon mcp --print-config` and `--check` from an npm install print `node`, the installed `mcp/dist/index.js`, `--brand` and `BLAZON_BIN`, and `--check` passes with a real handshake on a clean install; `--check` finds the blazon beside the server when `BLAZON_BIN` is not set. The `npx @iksnerd/blazon-mcp` form of a package that is not on npm is gone, from the command line and from the dev server's "Connect your agent" panel. An install that has lost the server file says the install is incomplete and to reinstall, and exits 1.
- The MCP server reports blazon's version as its own (`serverInfo.version`), where it said `0.0.0`.
- The manual said the server has eight tools; it has seven.
- The MCP tool `check_brand` says when plugins did not run. It always ran `blazon check --no-plugins`, so a brand whose `blazon.json` lists plugins such as `blazon.copy` got lower counts than `blazon check`, with no word on why. The answer now carries `pluginsSkipped` (the names from `blazon.json`) and one line in `warnings`; a config with no plugins adds nothing.
- The docs no longer state blazon's current version by hand (README status, manual, starter, CONTRIBUTING): a placeholder takes its place, and `test/docs/versions.test.ts` fails on a stale one.

## 0.2.0 (2026-11-16)

### Breaking

- The core no longer writes `tailwind.css` and `tailwind-reset.css`. Add `{ "name": "blazon.tailwind" }` to `plugins` in `blazon.json`, import the files from `dist/tokens/blazon.tailwind/` instead of `dist/tokens/`, and delete the old copies in `dist/tokens/`, which blazon no longer touches. The names `tailwind.css` and `tailwind-reset.css` are no longer reserved in `tokensOutDir`.
- The `shadcn` key of `blazon.json` is refused with `config-invalid`, and the message names the plugin. Move its map to `{ "name": "blazon.shadcn", "options": { "variables": { ... } } }` in `plugins`; the plugin reports a pick that names no token as `blazon.shadcn/token-missing`, which was `theme-unresolved`.
- `brand.json` is version 2: `theme.shadcn` is gone. A reader that checks `version` (as RFC 0001 requires) refuses version 1 files and must be updated; `blazon.shadcn` derives the same mapping, in `shadcn.json`. The `get_shadcn` tool and `blazon brand --key theme.shadcn` are removed with it: read `dist/tokens/blazon.shadcn/shadcn.json`.
- The `build` request of the plugin protocol is version 2 (`check` stays 1). It may carry no `site_dir`, which is how `blazon tokens` calls a plugin. A plugin written for version 1 of the build request is refused with exit 2 and the version named; change its check to 2, and answer a request with no `site_dir` (exit 2 with a reason, or an info finding and nothing written). A plugin that reads `brand.json` must accept version 2 of it. The reference plugins in `examples/plugins/` and `scripts/read-brand.py` do.
- `blazon get` no longer prints a `tailwind.css` name, and the `names.tailwind` field of its `--json` is gone. The Tailwind variable collision is reported by `blazon.tailwind` (`blazon.tailwind/variable-duplicate`, an error) when the plugin runs, not by `blazon check` as `css-variable-duplicate`, which now covers `theme.css` and a context's block only.

### Added

- Two shipped build plugins, `blazon.tailwind` and `blazon.shadcn`. `blazon.tailwind` writes `tailwind.css` and `tailwind-reset.css`; `blazon.shadcn` writes `shadcn.json` (which token each shadcn/ui variable takes) and `shadcn.css` (the variables as CSS, with a block for each context that changes one). Both read `brand.json` only, need only Node and write to `<tokensOutDir>/<plugin name>/`.
- `blazon tokens` runs the `build` plugins after it writes the token files. A plugin that needs the built site answers with the info finding `<name>/needs-site` and writes nothing, so `blazon build` is still the command for those. `blazon tokens` does not empty a plugin's folder: what the plugin writes overwrites the old file, and every other file stays, so the deck or press kit of the last `blazon build` survives. A file an earlier `blazon tokens` wrote and the plugin no longer writes also stays; `blazon build` empties the folder.

### Fixed

- `npm run release` regenerates `docs/stats.json` and runs the docs tests before it commits, and stops without a commit or tag if they fail. The release commit used to keep the old version in `docs/stats.json`, which failed `test/docs/stats.test.ts` at the pre-push hook and in CI on the tag.

## 0.1.1 (2026-11-16)

### Added

- `blazon.print-book` takes a `layout` option, `"compact"` (the default, the layout as it is) or `"roomy"`, which draws every picture whole and sets the prose and sections as the book was set before pictures were squeezed to share a slide, so it runs on more slides. Any other value is the `blazon.print-book/option-invalid` error.
- `directive-deprecated` (warning): a page comment `<!-- folio:name -->`, the old spelling, is reported with its page and line. Blazon reads only `blazon:`, so such a comment placed nothing and `blazon check` said nothing. A `blazon:` name that is not a directive was already `directive-unknown`.
- `token-extension-deprecated` (warning): a `$extensions` key that starts `dev.folio` on a token or a group is reported. It is ignored; rename it to `dev.blazon`.
- `blazon check` reports a build plugin whose manifest lists a variable that is set and not approved in the plugin's `env`, with the same `plugin-failed` message and fix as `blazon build`. It reads the manifest only and starts no build plugin.

## 0.1.0 (2026-11-16)

Published to npm as @iksnerd/blazon.

First release.

### Breaking

- A brand's own paths must stay inside its folder. `blazon.json` is data, so a path in it no longer decides what blazon reads or writes outside the project. `tokensDir`, `docsDir`, `assetsDir`, `resolver` and the `logo` files that are outside the project folder, by `../`, an absolute path or a link, now fail with the `config-path-outside` error and are not read. `outDir` and `tokensOutDir` in `blazon.json` that are outside it make blazon refuse to load the config. A token file or a page that is a link to a file outside the project is refused too, as is an icon set's `categories` file. Before, all of these were read or written, and `outDir` was emptied first. Copy the files in, or build to another folder with `blazon build -o <dir>`, which is still any folder you choose. The `dir` of an asset category may still name a shared folder, once the person running blazon approves it (next item).
- A category's `dir` outside the project folder is refused with `config-path-outside` (on `assets.<key>.dir`) unless the person running blazon approved the folder: `--allow-dir <folder>` on any command (repeatable), or `BLAZON_ALLOW_DIRS` (folders separated as a `PATH` is). `blazon.json` has no key for it, because a hostile brand would write one. Before, any brand could make `blazon dev` show, `blazon build` copy and the MCP tools return the image files of any folder it named. A monorepo script becomes `blazon dev --allow-dir ../shared`; a link or `..` out of an approved folder is still refused. An MCP client that needs a shared folder sets `BLAZON_ALLOW_DIRS` in the server's `env`. Plugins are never given the variable.
- `blazon mcp --check --json` has `runsPlugins: false` in place of `runsBrandConfig: true`, and its trust notice no longer says that compiling a brand runs plugins: the server runs none. The brand book's "Connect your agent" panel says the same.
- A plugin starts with an empty environment, `PATH` apart, and is given a variable only when its manifest lists the name in `env` and the project's config approves it in the `env` list of the plugin's entry (`plugins: [{ name: 'blazon.favicons', env: ['BLAZON_CHROME', 'HOME', 'TMPDIR'] }]`). `HOME`, `LANG` and `TMPDIR` are no longer passed on their own. A plugin whose manifest lists a name that is set and not approved is not started: `plugin-failed` names the variable and the key (`plugins[n].env`). `blazon plugin check` adds case 10, which fails when the project's config leaves out a name the manifest lists. The plugins that ship with blazon list what they read in their manifests like any other plugin: the ones that draw in Chrome list `BLAZON_CHROME`, `HOME` and `TMPDIR`, so a config that uses one adds those names to its `env`. RFC 0002 and RFC 0005 say so.
- `blazon plugin check` runs blazon's own cases for each role a plugin's manifest declares, after the core cases: 6, a valid request is answered with exit `0` or `2` (exit `1` fails it, as blazon treats it as a break); 7, the answer is within the role's stdout limit; 8, on exit `0` the answer is one the role accepts. A plugin that passed before can fail now. 9, for `build` only, warns when the plugin writes in `tokens_dir` outside `out_dir`; a warning does not fail the check, and `--json` gives such a case `"status": "warn"`, a new value beside `ok`, `skip` and `fail`. Fix the plugin, or read the case's detail ([Writing a plugin](docs/manual/13-writing-a-plugin.md#write-and-check-a-plugin)).
- `blazon check` warns `starter-logo-unchanged` for each configured logo that is still blazon's own mark, so a fresh `blazon init` project now reports 2 warnings (`--strict` fails it) until the logos are replaced.
- A brand must have a logo. A `blazon.json` with no `logo` now fails `blazon check` with the `logo-missing` error, which used to fire only for a configured file that was not there. Set `logo` to an image in the project.
- `blazon build -o <dir>` is a path from the folder you run blazon in, as for any command line tool. It was a path from the book, so `blazon build my-brand -o out` wrote `my-brand/out`. A relative `outDir` in `blazon.json` is still a path from the book.
- The `--json` counts name the notes `info`, as the findings do: `{ "errors": 0, "warnings": 0, "info": 23 }` replaces `notes`.
- A token's `review` block is now validated. A book that passed `blazon check` before can fail now. Each of these is an `review-invalid` error: a `status` that is not `ok` or `needs-review`, a `by` that is not a string, an `at` that is not a real `YYYY-MM-DD` date, a `value` that is not 12 hex digits, and a `value` on a token group (a group has no value to fingerprint). A malformed `review` in an asset sidecar is an `asset-sidecar-invalid` error. Fix the block, or remove the field.
- Blazon needs Node 24 or later (`engines` was `>=22`). Node 24 is the current LTS. Blazon does not use type stripping or `require(esm)` yet, and the shipped plugins stay compiled.

### Added

- The MCP server removes zero-width, bidirectional and Unicode tag characters from the brand text in every answer and says how many in `warnings`; its instructions tell the model to read that text as data. A number or boolean sent as a string (`"5"`, `"true"`) is accepted. A cut `get_fonts`, `get_logo`, `get_shadcn`, `get_token` or `can_use` answer no longer says "narrow with a path".
- A test shows that no MCP tool starts a plugin the brand config names.
- `blazon plugin check <program> --core` runs only the core cases of the plugin protocol (1 to 5): no role cases (6 to 9) and no `layout` line. The exit status is unchanged, and `--json` adds `core: true`. Without the flag nothing changes.
- `blazon explain <code>` says what a finding code means, how to clear it, and where to read more; with no code it lists every code, and an unknown code names the closest ones. `--json` gives the same as data.
- `blazon doctor` checks the environment (Node against `engines`, the brand folder, the plugin folder's safety, Google Chrome for the plugins that need it, and `blazon.lock`) and prints ok, warn or fail with a fix for each. It runs no plugin and writes nothing; it exits 1 only when a check fails.
- `--cwd <dir>` sets the folder every command works from. A folder argument is then relative to it.
- A blazon skill for coding agents, `skills/blazon/SKILL.md`, and a test that fails when it names a command, flag, tool or manual file that does not exist. Chapter 20 says how to install it.
- A `--json` error carries a stable `code` and, where there is one, a `fix`, beside the `message`, which is unchanged.

- A plugin may be listed more than once in `plugins`, each entry with an `as` instance id (dotted lowercase words, at most 64 characters, unique, and not the name of another plugin). Each instance has its own `options`, its own output folder `<tokensOutDir>/<id>/` and its own breaker; the pin stays one for the plugin's name. A finding of a plugin that is listed more than once ends with `(instance <id>)`. An entry with no `as` behaves as before.
- `blazon can <fg> <bg> --theme <name>` judges the pair in that context of the resolver's `theme` modifier (`--theme dark` on the starter), with the context's colors in place of the default's. An unknown theme exits 2 and lists the valid ones, and `--json` carries `theme`. The MCP tool `can_use` takes `theme` too.
- The starter has a dark theme. `blazon.resolver.json` loads the five token files and adds a `theme` modifier, light by default, whose `dark` context (`tokens/theme/dark.json`) puts Bone text on a Graphite page with a Carbon canvas and a Bone inverse band, and draws rules in Concrete and Zinc and the three shadows in Zinc. Signal Orange and `text.onSignal` stay as they are. `theme.css` carries it as a `[data-theme="dark"]` block, `blazon check` runs every rule in it, and the book's light and dark switch shows it. Two primitives are new, `color.base.carbon` (#101113) and `color.ink.zinc` (#8C9096), so the starter gains two tokens. Its Color, Form and motion, Logo and Web pages state the dark rules with their measured contrast, and `blazon init` lists `tokens/theme/dark.json` and `blazon.resolver.json`, so a fresh project reports 42 notes (it was 41).
- The starter has a `type.subhead` step (Big Shoulders Display 32/36px) between `type.h2` and `type.h3`, for a sub-section heading inside a page or chapter. Its Type and Web pages list it, so the starter has 79 tokens in all. The name is additive: `type.h3` keeps its name.
- The starter gains three tokens (it had 59): `shadow.shim` (2px, a key halfway seated) and `shadow.recess` (2px inset, an input or a tab rail) beside `shadow.plate`, and `type.code` (IBM Plex Mono 14/20px) for commands and code. Its Form and motion page states the key states (rest on the plate, `shadow.shim` under the pointer, no shadow pressed, each move at `motion.duration.snap`), its Color page says why Signal Orange has no hover shade, its Layout page gives ticks the rule colors, and its Web page lets small inverse parts (a tag, a panel's title strip, the active tab) sit beside the one inverse band.
- `npm run docs:stats` writes `docs/stats.json`, the version, commands, finding-code counts, MCP tools and manual chapters that a project website reads, and a test fails when the committed file is stale.
- `blazon can <fg> <bg> --role ui` (and an optional `role` on the MCP tool `can_use`) judges a focus ring, border or icon stroke instead of text: the contrast must reach 3:1 (WCAG 1.4.11), the `usage` rules are read for `border`, `icon` and `interactive`, and `pairs` do not apply. The default, `text`, answers as before; `--json` now also carries `role`, and `contrast.threshold` for `ui`. An unknown role exits 2. Manual chapters 8 and 19.
- `blazon fonts --css` prints the `@font-face` rules for the brand's font files (family, weight, style, `format()` from the extension, `font-display: swap`) and a comment for each stylesheet. `--base <url-prefix>` points `src` at the site's own public folder. With `--json` the text is `fontFace`. Command line only; the `get_fonts` tool is unchanged.
- `tailwind.css` also maps `shadow` tokens to `--shadow-*`, `cubicBezier` to `--ease-*`, `fontWeight` to `--font-weight-*`, font-size dimensions to `--text-*` and a `duration` named `default` to `--default-transition-duration`. A brand that wrote `plate`, weight or easing utilities by hand from `var(--...)` can use the generated ones. Border, transition and typography composites have no Tailwind namespace and stay `var(--path)`; chapter 8 has the table.
- `blazon tokens` and `blazon build` write `tailwind-reset.css`, a `@theme` block of `--color-*: initial` and the like for each Tailwind namespace the brand fills, so `rounded-xl` or `bg-blue-500` stop compiling. It is a separate file with no config key: import it after `tailwindcss` and before `tailwind.css`. Note that `--color-*: initial` also removes `white` and `black`. It is removed again when the brand no longer fills a namespace.
- The starter has six icons in `assets/icons/` (check, warning, arrow-right, download, file, token), each with a sidecar and drawn to the rules on its Icons page, and a local font: `fonts/IBMPlexMono-Regular-latin.woff2` (SIL OFL 1.1, licence in `fonts/OFL.txt`) is listed in `fonts` as a font file, so `blazon fonts` shows the path and the build embeds it. A fresh `blazon init` project now reports 39 starter-file-unchanged notes (was 27), still 0 errors and 2 warnings.
- The starter has a Web page, `docs/12-web.md` (section `applications`), for a site built in the brand: the type style for each page role, section spacing and widths, which surface goes with which section, buttons, cards, focus, the logo on the web, imagery and copy, and what to do about the shadcn variables the brand does not supply. It uses existing tokens only. `blazon init` now writes 12 pages and a fresh project reports one more `starter-file-unchanged` note; errors and warnings are unchanged. Chapter 19 of the manual points an agent at a brand's Web page.
- `blazon mcp --print-config [--client claude-code|claude-desktop|cursor|vscode] [--brand <dir>] [--json]` prints the config that registers `blazon-mcp` (stdio) in a client and writes no file. It uses the built `mcp/dist/index.js` when there is one; otherwise it prints the proposed `npx -y @iksnerd/blazon-mcp` form and says the package is not published. An unknown client exits 2.
- `blazon dev` has a "Connect your agent" button in the brand book's top bar: a panel with the same snippets for each client and a copy button, for the project's folder. The dev server serves them at `/__blazon/mcp-config`.
- `blazon list [group] [dir]` lists the tokens: path, type, CSS-ready value, and the token each aliases, so a coding agent can find a path without opening the token files. A group path keeps one group, `--type <type>` keeps one `$type`. `--json` prints `tokens` (and `group`, `type` when given); the text groups the lines under a header for each top-level group. An unknown group or type exits 2. `blazon get` takes a token path only and exits 2 for a group path. The function is `listTokens` in `src/core/read`.
- `blazon brand [dir]` prints the brand as `brand.json` holds it, compiled now and written nowhere, and `--key theme.shadcn` prints one part. `blazon tokens` does not write `dist/site/brand.json`, so a copy from an earlier build can be out of date; this command never is.
- A separate MCP server, `mcp/`, so a coding agent can ask blazon about a brand as tool calls: `get_token`, `get_rules`, `can_use`, `get_fonts`, `get_logo`, `get_shadcn` and `check_brand` (`list_tokens` came later, making eight). It runs the blazon CLI with `--json` and returns the parsed answer; it does not import blazon and blazon gains no dependency. It is private and not published. `get_shadcn` reads a built `dist/site/brand.json`, since no command prints `theme.shadcn`. Manual chapter 20, "Blazon for agents (MCP)".

### Fixed

- `blazon dev` and `blazon preview` answer 404 on Vite's `/__open-in-editor?file=...` route. Vite registers it on every dev server with no switch to turn it off, and any web page that can reach localhost could make a running editor open a local path. The dev server also sets `server.fs.allow` to the viewer's own folder (`dist/ui` when installed, the checkout from source) with `strict` on, instead of Vite's workspace-root search: an installed blazon served its own package files (`package.json`, `bin/`, plugin programs) over `/@fs/`, and the search would reach a folder above it if blazon's `package.json` lost its `workspaces` field.
- `blazon dev` and `blazon build` read and served the SVGs of any folder through an icon set whose `package` was a path (`../../Downloads`). `package` must now be a package name (`name` or `@scope/name`); a path fails with `icon-set-invalid`. `blazon preview` followed a link in the built site (`dist/site/leak.txt -> ~/secret`) and served what it pointed at; it now answers 403 for a link that leaves the site.

- A resolver with an inline modifier or set that reuses the name of a declared set or modifier is a `resolver-invalid` error, not an uncaught TypeError.
- Modifier, context and inline item names in a resolver must be letters, digits, `_` and `-`, so a name can no longer become a path outside `tokensOutDir`, break a selector or close a CSS comment. `blazon tokens` also refuses to write a file outside `tokensOutDir`.
- Token and resolver JSON files that start with a UTF-8 byte order mark parse instead of reporting `token-file-invalid`.
- `theme.css` no longer lets `*/` in a deprecation message, group name or context name end a generated comment.
- A string `fontWeight` outside 1 to 1000 (`"0"`, `"1200"`) is an `token-value-invalid` finding, as a number already was.
- The MCP server passes each option as one argument (`--theme=dark`), so a value that starts with a dash, such as `--cwd=/other/dir`, can no longer be read as an option and change the brand folder; `can_use` `theme` and `list_tokens` `type` refuse such a value.
- The MCP server no longer passes `NODE_*` environment variables (such as `NODE_AUTH_TOKEN`) to blazon.
- The MCP server keeps at most 64 cached answers.
- `blazon plugin check` and `blazon plugin pin` with no program or path exit 2 with a `missing-argument` error, as JSON under `--json`; `blazon init --json` errors carry a `code`, and a site that cannot be read is `site-unreadable`.
- `blazon plugin` refuses `--name`, `--digest` and `--entry` unless the action is `pin`, and a target for `profile`, instead of ignoring them.
- `blazon build --out-dir 2024` (the kebab spelling) takes the number as a folder name instead of failing with a TypeError.
- `blazon dev` and `blazon preview` listen on this machine only; `--host [address]` opens them to the network. They listened on every interface before.
- The exit status help no longer says every exit 2 did nothing: `blazon init --from` copies the starter first.
- Two pages with one slug (`01-colors.md` and `colors.md`) are a `page-slug-duplicate` error naming both files; the book opened only the first, silently.
- A page or an asset that cannot be read is a `page-unreadable` or `asset-unreadable` error; it used to be written to the console, dropped, and `blazon check` passed (and `--json` output was polluted).
- A page's title is no longer taken from a `# comment` inside a code fence, and a bare `#` no longer reaches across a line break to the next line.
- `approval-stale` no longer fires for a token whose alias does not resolve or loops, and so no longer tells you to record the fingerprint of the broken `{...}` text; one unreadable token file used to bring one for every approved alias into it.
- `token-value-duplicate` compares tokens that sit at the root of a file as siblings; it cut the last letter off their names, so `ab` and `ac` were compared and `ab` and `cd` were not.
- `page-tokens-unplaced` no longer notes a page that places tokens with `cards`, `strokes`, `spots`, `logo-on`, `formats` or `patterns`; the exempt directives now come from the directive table.
- With a token file unreadable, the findings that a directive names a missing color, border, format or pattern are left out as well, not only "no token at".
- `blazon explain` lists what `contrast-pair-invalid`, `token-type-unknown`, `section-missing` and `token-file-invalid` point at as the code does: a group, a token or group, the project.
- A contrast pair measures a translucent foreground blended over its background, as WCAG does; `transparent` or `rgba(0,0,0,.05)` on white used to pass AAA. A translucent background gives `contrast-unknown`, as what is behind it is not known. A failing ratio is floored to two decimals, so 4.496 no longer prints as "4.50:1; AA needs 4.5:1".
- A plugin whose manifest call exits 1 or 2, or prints a manifest blazon cannot load, now counts toward the breaker (three in a row stop it for the run) and, for exit 1 and a bad manifest, starts the dev server's cooldown; before, it was reported every time and never stopped.
- `--plugin ./bin/blazon-acme.x.🔌` is accepted: the plugin's name is what lies between `blazon-` and the final `.🔌`.
- A plugin instance id that is a file blazon writes in `tokensOutDir` (`tokens.json`, `theme.css`, `tokens.<modifier>.<context>.json` and the rest) is refused as `config-invalid`; it would have replaced the file with a folder.
- A plugin's standard error is kept from its end (the last 8 KB), not its start, so the "last lines of standard error" a failed plugin shows are the last lines it wrote, and a secret that crossed byte 8192 is no longer cut before it is scrubbed.
- Scrubbing also removes a secret in lowercase percent-encoding, inside the base64 of a longer string (such as Basic auth, at any of the three alignments) and as a JSON string escape (`\uXXXX`, `\"`, Go's `<`).
- A plugin that runs out of time, or prints too much, is sent SIGTERM and killed 2 seconds later instead of at once, so one that started Chrome can close it.
- The manual no longer says `blazon plugin check --core` checks a plugin written for another host: the manifest is still read against blazon's roles, so a plugin that declares neither `check` nor `build` fails case 1.
- Plugin output is scrubbed of secrets after its control and format characters are removed, not before, so a secret split by a zero-width character or an escape byte no longer reaches a finding, an exit 2 message or the stderr tail; a finding whose code the scrubber would change is refused as a malformed answer.
- MCP truncation keeps the most findings that fit, not a power-of-two fraction of them (120 that fit used to come back as 62), counts the `warnings` it adds in that fit, and keeps `counts` and `passed` when it falls back to cutting the text. The fallback cuts on code points, not inside a surrogate pair.
- A plugin's finding message stays within 1000 characters with its ` (instance X)` suffix counted.
- Every error and warning finding code, and every note but `asset-local-missing`, has a fix line, and a test fails when an error or warning code has none.
- A plugin call that exits 2 counts as a break for the run breaker, as RFC 0002 section 7 now says, so a plugin that always exits 2 is stopped after three calls. The dev server's cooldown still takes exit 2 as a change to wait for, not a break.

- A `plugin-failed` finding gave one fix for every cause, "pin the plugin", which was wrong for a plugin that crashed or for blazon installed under a shared folder such as `/tmp`, where the manual said to run `chmod go-w` on the folder. Each cause now carries its own fix, in `--json`, `brand.json` (a new optional `fix` on a finding) and the "Next" list; for a shared folder it is to install blazon under your own home folder. A plugin that breaks now shows the last lines of its standard error in the message (`exited with 3; stderr: boom: cannot find thing`), at most 5 lines and 500 characters, with secrets taken out; a plugin that answered shows none.
- A program named with `--plugin` could take the id of an instance's `as`, and the two shared an output folder and a breaker, so one emptied the other's files. Ids are now checked across the config and `--plugin` together: the later one is refused with `plugin-failed`, which names both. An id taken from a plugin's name, with no `as`, is now held to the 64 characters an `as` is, and two different `--plugin` programs for one plugin are refused.
- The starter's key shadows read as a glow in the dark theme. `shadow.plate` and `shadow.shim` are now Carbon in `tokens/theme/dark.json` (they were Zinc), the one ink darker than the Graphite page, so a key stands on a shadow and not on a second edge. `shadow.recess` stays Zinc. Its Form and motion and Web pages say so.

The focus outline no longer follows the rule: the starter's `shadcn.ring` is `text.primary`, 14.48:1 in dark and Graphite in light as before. Its Color, Layout and Web pages say so.

- `blazon init` with `--from` or `--logo` also removes blazon's own mark (`assets/logos/blazon-mark`) when it replaces the starter's logo; it used to stay behind under the brand's name.
- `blazon init --from` no longer claims the colors, fonts and logo were read from the site when some were not: the intro page names what was read and what is still blazon's own starter, and the next steps say to add a logo when none was found. After a site that could not be read it prints no next steps, and says to start again in a new folder, since a folder that already has the starter is kept as it is.
- `blazon build` no longer deletes the brand's own files. An `outDir` that is or holds `tokensDir`, `docsDir`, `assetsDir`, a category's own folder, the resolver, a logo or a font file used to pass `blazon check` and then be emptied by the build. It is now an `output-dirs-overlap` error, and `buildSite` and `emitTokenOutputs` refuse it too, so calling them from code is as safe as the command. The token files a resolver names count as inputs wherever they are, and a path is compared by where it really is, so a symbolic link to an input, or a folder reached through one, is caught. An `outDir` or `tokensOutDir` inside an input folder is refused as well, because the next build would read the output as tokens, pages or assets.
- `blazon tokens` and `blazon build` no longer delete or overwrite a file the brand reads. A token file a resolver names that sat in `tokensOutDir` under a name like `tokens.mode.dark.json` was removed as a stale output of blazon's own; it is now left alone, and a source that has the name of a real output is an error before anything is written. An icon set's `categories` file and a build plugin's folder under `tokensOutDir` count as inputs for the `outDir` check too. What the dev server watches, what the output check protects and what the writers refuse to touch are now one list, `projectInputs` in `src/core/inputs.ts`.
- An icon set's package in `node_modules` is an input for the `outDir` check, and a build whose icon package is gone by the time its icons are copied stops with an error naming the set, where it used to report success and leave the icons out. A resolver source that is a symbolic link is held by the link as well as by its target, so an `outDir` that holds only the link is refused.
- A build plugin named only with `--plugin` can no longer have a file the brand reads deleted with its output folder. The plugin writer checks the folder before it empties it, as the output check does for the plugins in the config, and stops the plugin with a `plugin-failed` finding.
- A resolver context that points a token at another token holding the same value keeps the change: the context's `metadataChanges` carries it with the new `aliasOf`, and the brand book shows it. It was dropped because the CSS value did not change.
- In `blazon dev`, the result of a check that was running when a change replaced it can no longer arrive after the new page data and put the old findings and tokens back. This happened when the change switched the plugins off.
- A finding about a token from a resolver source named a file that does not exist (`tokens/tokens/base.json`) and gave no line. It now names the file as the project has it, with the line, or the resolver document for a source written inside it.
- Every token says which file it is in the same way, from the project root, whichever loader read it. A project with no resolver gave `colors.json` as a token's `sourceFile` in `brand.json` (the docs said `tokens/colors.json`), and a tokens folder that was not directly in the project, such as `brand/tokens`, showed `tokens/` in the path of an `token-file-invalid` finding. A source written inside a resolver document in a subfolder named only the document's file name.
- A context is put back together from the default and its changes in one place, `contextItems` in `src/core/tokens/contexts.ts`, which the token export and the brand book both use. Contexts are combined field by field, so choosing two modifiers that change one token in different ways (a value and a description) shows both, and the theme follows the tokens as shown. The brand book with a context chosen now shows that context's descriptions and deprecations too, and `brand.json` carries them as `metadataChanges` on the context (absent when there are none).
- A resolver context that changes only a token's description, deprecation, type or extension, and not its value, is kept in that context's `tokens.<modifier>.<context>.json`. It used to be dropped, so the file kept the default's text.

### Changed

- The config is plain JSON in `blazon.json`, and nothing else. It was code (`blazon.config.ts`, `.js`, `.mjs`, `brandbook.config.ts`, `brandbook.config.js`), run through Vite; it is now data a person can read and a tool can write, with no comments and no code. A folder that still has one of the old files stops with a `config-invalid` error that names the file and says to move its values into `blazon.json`. `defineConfig` and the `@iksnerd/blazon/config` entry are gone, the starter's config no longer holds commented-out plugins (`blazon init` leaves them out, and the manual says how to add one), and the `blazon.cue-rules` plugin takes its rules text in `options.rules`. RFC 0001 open question 7 is decided.
- Every finding code follows one rule, `<area>-<problem>` in kebab-case with the problem word from a fixed list, and 42 codes are renamed, such as `unresolved-alias` to `alias-unresolved` and `needs-review` to `review-pending`. Codes freeze at 1.0, and there is no alias: a script, approval or filter that names an old code now gets the unknown-code error. The old-to-new table is in the manual's [Checks](docs/manual/03-checks.md#how-codes-are-named) chapter.
- Releases are one command, `npm run release -- <version>`, and CI on the tag builds the package fresh, installs the tarball and runs blazon from it, then attaches it with `SHA256SUMS` and a build provenance attestation; a `publish` job is in `ci.yml` but stays off until `NPM_PUBLISH` is set. `npm pack` now builds first, the package no longer carries a `prepare` script (npm 12 warned every installer about it; contributors run `npm run hooks`), and `scripts/check-pack.mjs` fails a tarball that lacks `dist/`, the starter, a plugin program or the lock.
- The starter's `AGENTS.md`, its web page and `blazon init` no longer link a manual on a website, which does not exist yet. `AGENTS.md` names the `docs/manual/` folder of the blazon source repository and each chapter by title, and `init` no longer prints a `The manual:` line.
- The viewer build writes Geist's OFL license as `assets/geist-OFL.txt` beside the font files, so it is in `dist/ui` and in every built site. `THIRD-PARTY-NOTICES.md` names both starter IBM Plex Mono files, `jszip`, `lightningcss` and `pako`.
- A plugin that exits `2` ("cannot answer") three times in a row in one run is now stopped for the rest of that run, as a break is. In `blazon dev` exit `2` does not start the 30-second cooldown, since its message asks for a change the next save may make.
- The text output names places you can open and commands you can run from where you are. A finding with a file starts with `file:line` (`acme/tokens/colors.json:17  color.base.bone: ...`), as compilers print it, in `check`, `tokens` and `build`. `blazon init acme` and `blazon check acme` give their next steps as `blazon dev acme` and `acme/tokens/colors.json`, and `init --color` says the primary is set instead of asking for it. Every error is `blazon <command>: <what happened>` with the fix on its own line, replacing `[blazon <command> error]`, and `blazon drift` names a CSS file that is not there instead of printing `ENOENT`. `--json` is unchanged, except that `error.message` follows the new wording.
- `blazon dev` treats a burst of file events as one change: it waits 75 ms after the last event, then compiles once and sends one update. A `git checkout` of 24 files sent 24 updates, each from its own compile. A single save is sent 75 ms later than before.
- `blazon check` and `blazon tokens` on a folder that is not there say so without first printing their "Checking…" or "Compiling…" banner.
- An `token-file-invalid` finding has `file`, as the other findings with a position do, and a token file whose top level is not an object is reported under `tokens/<file>`, not the bare file name.
- `blazon drift` and `blazon init --from` say why a fetch failed (the refused connection, the name that does not resolve) after `fetch failed`.
- `--severity` without `--json` is refused (exit 2) instead of ignored: it cuts the list that `--json` prints.
- `blazon init --color <hex>` no longer makes every command print color codes into a pipe. The color library read any `--color` argument as a request for color; blazon now decides from the terminal, `NO_COLOR`, `TERM=dumb`, `--no-color` and `FORCE_COLOR`.
- `blazon check` refuses a dimension or duration that is not one (`"abc"`, `"12"`, `"4pixels"`; a bare `0`, a function such as `calc()` or `var()`, and a keyword such as `auto` still pass), and an `oklch()` or `oklab()` whose lightness is outside 0 to 1 or 0% to 100% (`oklch(60 0.2 250)` is white in CSS; 60% was meant). They passed without a word, so a brand with a wrong value reported as sound.
- A token file that does not parse no longer brings a screenful of errors with it. While any token file is unreadable, the findings that only say a token is missing (`alias-unresolved`, `theme-unresolved`, and the `token-value-invalid` for an alias that could not be followed) are left out; fixing the file brings back whichever are real.
