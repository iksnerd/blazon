# Maintaining a brand book

← [Manual index](index.md)

A brand book that lives in a repository is changed many times by several people. This chapter is a routine for that: what is written by hand and what is generated, how to pin the blazon you build with, how to make a change and tell what it did, how approval is recorded, and how to land it. It uses only what blazon provides, and the sample scripts are yours to adapt. [Chapters 1 to 8](index.md) say how each part works.

## What the repository holds

| Written by hand | Generated by blazon | Generated by your scripts |
|---|---|---|
| `tokens/` (and `blazon.resolver.json`), `docs/`, `assets/` with their sidecars, `blazon.json`, `blazon.lock` (the blazon commit, written by `blazon pin`) | `dist/tokens/` (CSS, `tokens.ts`, `tokens.json`), `dist/site/` (the book and `brand.json`), and each plugin's folder in `dist/tokens/` | whatever you make from them: a PDF, a package of the tokens, a folder of images you copy back into `assets/` |

Do not edit a generated file; change its source and build again. Keep `dist/` out of git. Commit a generated file only when someone needs it without blazon (a PDF of the book, a package of the tokens), and then say so in the repository's own docs, so nobody edits it by hand.

## Pin the blazon you build with

A build depends on the blazon that runs it. If every person builds with whatever they last installed or pulled, the same sources can give different outputs. There are two ways to fix the blazon, and they combine.

**A published version.** Install an exact version in the project that builds the book. The `package.json` then says `"@iksnerd/blazon": "<version>"` and the lockfile fixes the rest of the tree, so `npm ci` gives everyone the same blazon:

```sh
npm install --save-exact @iksnerd/blazon@<version>
```

While blazon is 0.x, a range such as `^<major>.<minor>.0` takes new patch releases of that minor and no other minor, and a minor release may break ([chapter 18](18-stability.md)); an exact version moves only when you move it.

**A commit.** Name the blazon commit in `blazon.lock` and let blazon refuse any other. `blazon pin` writes the commit of the blazon that runs it. For an installed blazon that is the commit the release was built from; for a clone it is the commit checked out, built with nothing uncommitted. A source checkout is also the only way to build a blazon from a commit no release has (every commit between two releases says the older one's version in `package.json`, so the version number cannot tell commits apart):

```sh
# with an installed blazon, in the book
blazon pin                        # writes blazon.lock: { "v": 1, "commit": "<40 hex digits>" }

# or with a clone: at the commit you want, with nothing uncommitted
npm ci && npm run build
# then, in the book
blazon pin
```

Commit `blazon.lock` with the book. From then on `blazon check`, `blazon tokens` and `blazon build` compare the blazon that runs with it, and stop with a `pin-mismatch` error (the file and line in `--json`, a `Next:` step in the text) when they differ. A book with no `blazon.lock` is not checked. `blazon dev` shows the same findings on the Review page and reads `blazon.lock` again when it changes, so pinning, editing or removing it needs no restart.

**What the check knows.** `npm run build` compiles the commit it was run at, and whether the tree had uncommitted changes, into `dist`. That is what the check reads, so it compares the blazon that runs, not whichever commit the clone has since moved to. Run from source (`npm run blazon:src`) there is no build, so blazon asks git for the clone's commit when it starts. It does not guess: a blazon with no git checkout and no stamp (a copy of the folder without `.git`, or a build made outside git) cannot say which commit it is, and a pinned book refuses it.

**What it does not know.** The stamp shows that `dist` was built from that commit. It does not show that `dist` was left alone afterwards, that `node_modules` matches the lockfile (use `npm ci`), or that nobody edited the stamp: it catches the mistake that happens, building with the wrong checkout, and is not a defence against someone who means to get round it. A tree with uncommitted changes does not match even at the pinned commit, because it is not that commit.

If you check out the pinned commit and forget to build, the error says so: the clone is at the pin but the `dist` that runs was built from another commit.

If you build with a clone, keep it at the pin, and do any work on blazon itself in a separate worktree (`git worktree add -b topic ../blazon-wt-topic origin/main`), or the next build stops. With an installed version, moving the pin is `npm install --save-exact @iksnerd/blazon@<version>` and then `blazon pin` again.

**Moving the pin** is a change of its own. Build the book with the old pin and keep what it wrote. Then install the new version, or check out the new commit in the blazon clone (it must be one you can fetch, so push blazon first) and run `npm ci && npm run build` there. Run `blazon pin` in the book to write the new commit, build again, and compare the two sets of outputs (see below). If they are the same, commit `blazon.lock` alone. If they differ, read what changed in blazon and look at those outputs before you commit. A change that adds markup can move a space or a line break without changing a word: compare the words with spacing before punctuation ignored, and look at the pages that differ, before you call it more than that.

## A new blazon option comes with a new pin

A config key, a page directive or a plugin option exists only in the blazon commits that have it. A book that uses one before its pinned blazon has it fails `blazon check` for everyone who builds with that pin, and still builds on the one computer whose blazon clone has the change. This has happened: a book's `main` used an `emailSignature` key and a `blazon:email-signature` directive that no pushed blazon had, and stopped checking until the two were switched off.

The order that cannot go wrong:

1. Push the blazon change to the blazon repository's `main`.
2. Move the pin to that commit, as a change of its own (Moving the pin, above).
3. Only then use the option in the book.

Run your build, or at least `blazon check`, with the pinned blazon before you push. If the book is pinned with `blazon pin`, blazon itself refuses a blazon with uncommitted changes (`pin-mismatch`), so a local, unpushed change fails on your own computer before it reaches anyone else.

## One command to build

People forget a step that is not in a script. Put the routine in one: check, build, then whatever you make from the outputs, stopping at the first error.

```sh
blazon check                      # exits 1 on an error; --strict also fails on a warning
blazon build                      # writes dist/tokens/ and dist/site/
# ...then your own steps: copy generated files into assets/, make a package or a PDF
```

In a pipeline use `blazon check --strict`, and read the findings as JSON with `--json` if a tool needs them ([Checks](03-checks.md)). A build that passes still prints warnings: the `review-pending` ones are the book's open list and not a failure, until you ask for `--strict`.

## Make a change

1. **Work on a branch, or in a worktree**, so a half-finished change never sits in the checkout other people use.
2. **Edit the source**, with `blazon dev` open if you like: tokens, pages and assets reload in the browser.
3. **Run the checks and the build.** `blazon check` names the file and the rule for each problem; [Troubleshooting](10-troubleshooting.md) and [Checks](03-checks.md#every-finding) explain each finding.
4. **Look at what you made.** Open the book at the pages you changed. A table that runs off the page, or an image that is the wrong crop, is something no check catches.
5. **Say what changed in the outputs**, below.
6. If the brand book mirrors a live site, `blazon drift <url-or-css-file>` says which token values the site now differs on.

### Compare content, not bytes

A generated PDF can change in bytes when nothing a reader sees has changed: a producer string, a date, a recompression step. Blazon's deck plugin writes the same bytes for the same input on one computer, but a PDF you print or recompress yourself may not. Compare what a reader sees: the page count, the text and the pictures.

```sh
tmp="$(mktemp -d)"
git show HEAD:exports/book.pdf > "$tmp/old.pdf"
diff <(pdftotext -layout "$tmp/old.pdf" -) <(pdftotext -layout exports/book.pdf -) && echo "same text"
pdfinfo "$tmp/old.pdf" | grep Pages; pdfinfo exports/book.pdf | grep Pages
pdftoppm -r 30 -png "$tmp/old.pdf" "$tmp/old" && pdftoppm -r 30 -png exports/book.pdf "$tmp/new"   # then compare the images
```

If the content is the same, restore the committed file (`git restore exports/book.pdf`) and do not commit the churn. For tokens, compare `dist/tokens/tokens.json` with the committed or previous one: a changed value, a new token or a removed one is a change to what apps receive.

## Keep pages that must match in step

A book in two languages has pages that must stay one page: the same sections, in the same order, with the same number of rows in each table. A person reviewing a change sees one file and forgets the other. Let the check hold them to it, with a `check` plugin that reads the structure and not the words ([Writing a plugin](13-writing-a-plugin.md)).

1. **Write the schema where people can read it,** as data: the pages that form a set (by slug), the front matter keys each carries, how many paragraphs open it, and its sections in order with the heading each page has. Where a section has a size, give it: the rows of its table or its bullets. Leave a section with no size when it may differ, such as the rules that apply to one language only. Other pages link to headings, so the schema names the heading each page has instead of comparing them.
2. **Pass it to the plugin as `options`,** in `blazon.json`, which is plain JSON, so the schema is JSON too. The plugin reads each page's `meta` (front matter) and `markdown` from the request ([brand.json](11-brand-json.md)): H2 lines are the sections, lines that start with `|` are table rows (the first two are the header and its rule), and lines that start with `- ` are bullets. Skip code fences, or a fenced example is read as a section.
3. **Report each difference as an error with the page's file and what the schema has,** such as `"Claims" has 4 bullets, the schema has 5`. Exit 2 with a message when the options cannot be read, so a mistake in the schema is never a pass. The plugin must be pinned ([Plugins](12-plugins.md#pin-a-plugin)), and pinned again after any edit.
4. **Test that it bites.** Undo each rule of the plugin in turn (headings not compared, counts not compared, one page of the set skipped) and see that a test fails each time, and break a page of the real book and see `blazon check` exit 1.

Changing a page's structure then means changing the schema in the same commit. What the plugin cannot say is whether a translation is right: a person who reads both still does that.

## Say what is approved, and by whom

Blazon records review in the data, so it shows in the book and in the check. On a token or an asset sidecar, `review` is `{ "status": "needs-review" }` until a person approves it, then `{ "status": "ok", "by": "A. Person", "at": "2026-10-28" }` ([Tokens](02-tokens.md), [Assets and icons](06-assets-and-icons.md#sidecars)); `note` stays for anything else worth saying. An approval that only has a `note` still works. While it is `needs-review` it is a warning on the Review page, and it fails a `--strict` check. A generated image needs its own review. Write an approval only when the owner gave it, and write who (`by`) and when (`at`). To have the check notice a later change to what was approved, run `blazon approvals`, copy the fingerprint it prints into `review.value`, and commit it with the approval: a value or an image that changes afterwards gives an `approval-stale` warning until a person confirms it again and replaces `value` ([Noticing a changed value](02-tokens.md#noticing-a-changed-value)).

## Land it

Commit by path (`git add <paths>`, not `git add -A`), so you commit what you meant to and nothing a tool left. Say in the message what changed and what you checked. Fetch before you push and rebase if something arrived. Remove your worktree and branch afterwards.

## Build the tokens without a browser

Plugins that draw (the deck, the favicons) need Chrome, which a pipeline that only publishes the tokens may not have. `blazon tokens --no-plugins` writes the tokens and runs no plugin, whatever the config lists. `blazon check --no-plugins` and `blazon build --no-plugins` do the same for the check and for the book. The pin is still enforced, because it is not a plugin, and the flag cannot be used with `--plugin`, which names a plugin to run (exit 2).

A plugin adds findings and writes its own files under `dist/tokens/<name>/` (the favicons plugin also writes a `favicons/` folder into the built site); blazon itself writes the token files, and no plugin changes them. Check once that the files you ship (`tokens.json`, `theme.css`, `tokens.ts` and the rest) are byte for byte those the full build writes, and keep that check, as it is the proof that the pipeline publishes what the book does. Before this flag the same result needed a second config with `"plugins": []` and a temporary copy of the project; a book that still has them can delete them.

## When it fails

| You see | It means |
|---|---|
| `Front matter is not valid YAML` (`page-frontmatter-invalid`) | A `title` or `description` has a colon and a space. Put it in double quotes. The page is left out until it parses |
| `customSections[n].id "..." is a standard section` (`config-invalid`) | A standard section needs no entry in `customSections`; keep its name in `sections` |
| `icon-set-invalid ... is not installed` | The icon package is not in this checkout's `node_modules`. Run `npm ci` if it is in `package.json`, or `npm install <package>` if it is not |
| `... is not pinned, and a check plugin must be` (`plugin-failed`) | A `check` plugin must be pinned: [Plugins](12-plugins.md#pin-a-plugin) |
| Your build script says the blazon is not the pinned one | The blazon that runs is not the pinned one. Install the version that matches the pin, or check out the pinned commit in your clone and build it |
| `unknown key "..."` (`config-invalid`), with no "did you mean" | The blazon that runs does not have that option. Spelt right, it belongs to a newer blazon: [move the pin](#a-new-blazon-option-comes-with-a-new-pin) to a commit that has it before you use it |
